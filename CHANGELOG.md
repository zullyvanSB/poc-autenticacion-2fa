### Seguridad
- Se validó server-side el dominio corporativo del correo de Google durante la creación de sesión como defensa en profundidad (POCA-004, camino B). En `backend/src/auth/router.py`, `create_session` ahora captura los claims de `verify_id_token` e interpone, **solo** cuando `firebase.sign_in_provider == "google.com"`, una comprobación que ancla la autorización en el claim top-level `email` del token verificado (no en el parámetro `hd` del frontend, que es cosmético y eludible): extrae el dominio tras el último `@`, lo normaliza a minúsculas y exige **match exacto** (case-insensitive) contra la allowlist por entorno de `get_corporate_allowed_domains()` (POCA-001). Si el dominio no está permitido, o el `email` falta o no es extraíble, o la allowlist está vacía (fail-safe deny), responde `401` genérico reutilizando `_auth_failure_response`, sin `Set-Cookie`, sin revelar el motivo y sin loguear el correo ni el dominio (solo `correlation_id` + evento). La lógica de decisión se encapsuló en la función pura `is_allowed_corporate_email(email, allowed_domains)` en `backend/src/auth/firebase_auth.py` (añadida a `__all__`). Los proveedores `password` y `saml.<id>` no aplican esta validación (sin regresión). Se añadieron pruebas unitarias tabuladas y property-based (hypothesis) para la función pura y casos de endpoint para el camino B y las regresiones (suite del backend en verde: 169 pruebas).

### Cambiado
- Se cambió la CLI_Gestion para que las operaciones de alta, actualización y baja de usuarios Cliente (`crear_usuario`/`actualizar_usuario`/`eliminar_usuario`) ocurran ahora dentro del tenant dedicado de Google Cloud Identity Platform, en lugar del nivel de proyecto: `_dispatch` resuelve el identificador del tenant por configuración (variable de entorno `FIREBASE_TENANT_ID` o la bandera `--tenant`, con precedencia de la bandera, sin hardcodear) mediante el nuevo `resolve_tenant_id` y obtiene un `auth.Client` acotado al tenant con `auth_client_for_tenant` (que delega en `firebase_admin.tenant_mgt.auth_for_tenant(tenant_id, app=app)`), y los comandos invocan `create_user`/`update_user`/`delete_user` sobre ese cliente del tenant preservando el mismo manejo de errores (correo duplicado, usuario inexistente, error genérico de operación); si no se configura ningún tenant, la operación aborta con un error de validación claro antes de tocar el Admin SDK, aislando los usuarios de prueba de la PoC del resto del proyecto. Se actualizaron las pruebas unitarias (`cli/tests/`) para inyectar `tenant_mgt.auth_for_tenant` y verificar el aislamiento por tenant, y se documentó el requisito de `FIREBASE_TENANT_ID`/`--tenant` en `cli/README.md`.
- Se cambió el `AuthService` del Frontend_Angular para que ahora opere contra el tenant dedicado de Google Cloud Identity Platform mediante un `tenantId` configurable (resuelto por entorno vía `window.__APP_CONFIG__.firebase.tenantId`, sin hardcodear): se añadió el campo opcional `tenantId` a `FirebaseWebConfig` (`frontend/src/environments/environment.model.ts`), su resolución en `resolveFirebaseConfig()` (`frontend/src/environments/runtime-config.ts`, incluido solo cuando está presente y sin formar parte del null-check de campos obligatorios) y el marcador público `__FIREBASE_TENANT_ID__` en `frontend/src/config.template.js`. En `getFirebaseAuth()`, tras `getAuth`, se fija `Auth.tenantId` cuando hay un `tenantId` configurado, de modo que el inicio de sesión con correo/contraseña, la inscripción/resolución de MFA (TOTP) y el `signInWithRedirect` (SAML) quedan confinados al tenant dedicado, aislando los usuarios de la PoC del proyecto compartido. El campo es opcional: si no se resuelve, la app sigue operando a nivel de proyecto y se preserva el comportamiento de `ConfigurationError` ante config de Firebase o URL de backend ausentes.
- Se actualizó la Guía Operativa (`docs/guia-operativa.md`) para documentar el aislamiento de la PoC en un tenant dedicado de Identity Platform: se añadió el marcador `<TENANT_ID>` y el nuevo Paso 1.6 con los comandos verificados (habilitar multi-tenancy con `multiTenant.allowTenants`, crear el tenant dedicado, habilitar TOTP MFA a nivel de tenant vía `mfaConfig` y verificar el aislamiento proyecto `DISABLED` / tenant `ENABLED`); se corrigió el Paso 1.5 para recomendar el TOTP a nivel de tenant en proyecto compartido e incluir el comando de reversión del MFA a nivel de proyecto a `DISABLED`; se actualizaron la Sección 2 (CLI con `--tenant`/`FIREBASE_TENANT_ID` y selector de tenant en consola), la Sección 3 (proveedor SAML dentro del tenant y `auth.tenantId`), las tablas de aprovisionamiento y de bloqueos (requisito de `FIREBASE_TENANT_ID` en backend y CLI, multi-tenancy, TOTP a nivel de tenant) y las referencias oficiales de multi-tenancy y de habilitación de TOTP MFA.

- Se corrigio la prueba unitaria `test_verify_session_cookie_returns_claims_on_success_with_correct_tenant` para que afirme `check_revoked=False` en `verify_session_cookie`, alineandola con la decision de verificar la session cookie con el cliente de nivel proyecto (el usuario reside en el tenant de Identity Platform; con `check_revoked=True` el SDK fallaba con `UserNotFoundError`). ### Cambiado
- Se reforzó la verificación de identidad del `Backend_FastAPI` para operar contra un tenant dedicado de Google Cloud Identity Platform: ahora `verify_id_token` y `verify_session_cookie` (`backend/src/auth/firebase_auth.py`) validan, tras la verificación criptográfica del Admin SDK, que el claim `firebase.tenant` del ID token y de la session cookie coincida con el tenant configurado (defensa en profundidad, R5.3). Como el tenant se resuelve por variable de entorno (`FIREBASE_TENANT_ID`, agregada a `REQUIRED_ENV_VARS` y expuesta por el nuevo accesor `get_firebase_tenant_id` en `backend/src/common/config.py`, sin valor embebido), un token de nivel proyecto (sin el claim `tenant`) o de otro tenant se rechaza con el MISMO error genérico de dominio ya usado en cada ruta (`InvalidIdTokenError` para ID tokens, `InvalidSessionCookieError` para session cookies), sin revelar que el motivo fue el tenant ni crear sesión alguna; internamente solo se registra el tipo de evento y el resultado booleano de la comparación, nunca el token ni el valor del tenant (R5.5, R6.3, R10.4). Se añadieron pruebas unitarias (`backend/tests/test_auth_firebase.py`) con el Admin SDK mockeado que cubren el camino feliz con tenant correcto y el rechazo genérico ante tenant distinto, ausente (nivel proyecto) o estructura inesperada, tanto para ID tokens como para session cookies.
